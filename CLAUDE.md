# Nexora — project context for Claude Code

Nexora (working name) is a web platform where anyone describes an app idea in plain words and gets back a working, deployed, full-stack web app. It runs on the user's own **free** AI API keys, and the finished app lives in the user's own Supabase, GitHub and Vercel/Netlify accounts.

Read this file first. It tells you what we are building, the rules that never change, and where the detail lives.

## Two codebases, don't mix them up

1. **The platform** — Nexora itself: the website, the build workers, the LLM router. We write this.
2. **Generated apps** — what the platform produces for users. Built from templates in `templates/app-starter` plus generated code. Lives in the user's repo, not ours.

When a task says "the app", check which one it means. Platform code must never import from a generated app, and generated apps must never depend on Nexora packages at runtime.

## Fixed stack

**Platform** (recommended defaults; see decision log before changing):

- pnpm workspaces + Turborepo monorepo, TypeScript everywhere, strict mode
- `apps/web`: Next.js (App Router, latest stable), Tailwind CSS, shadcn/ui
- `apps/worker`: Node worker that runs build jobs in isolated sandboxes
- Platform data and auth: Supabase (our own project), Postgres with row-level security
- Validation: Zod for every schema that crosses a boundary (API, LLM output, job payloads)
- Tests: Vitest (unit), Playwright (end to end)

**Generated apps** (one opinionated stack, no alternatives in v1):

- Next.js (App Router) + TypeScript + Tailwind + shadcn/ui
- Supabase: Postgres, Auth, Storage; SQL migration files; RLS on every table
- Zod, Vitest, Playwright
- Deploy target: Vercel (Netlify second)

## Rules that never change

1. **Templates before tokens.** Anything a template can generate (CRUD, auth, roles, RLS, admin tables, forms, KPI cards) is generated by deterministic code, not by an LLM. LLM calls are only for the spec, custom business logic, custom UI and fixes.
2. **Checks before opinions.** Quality is judged by compilers, linters, tests, axe and Lighthouse. An LLM never grades its own output; it only fixes what a check reported.
3. **Every LLM call fits a small context budget.** Default budget 12k input tokens; hard cap 16k unless the routed model's live limit allows more. Send only the files a task needs.
4. **Rate limits are expected, not errors.** All LLM calls go through `packages/llm-router`. Never call a provider SDK directly. A 429 means fail over, then checkpoint and resume later — never crash a build.
5. **Secrets never enter prompts, logs, client bundles or generated source.** Generated code reads secrets from environment variables only.
6. **The user owns everything.** Their code goes to their GitHub, their data to their Supabase, their app to their host. We store only what's needed to resume work.
7. **Styles are rules, not pictures.** UI is built from design tokens (`design/*.json`). No hard-coded colors, fonts or radii in components, in the platform or generated apps.
8. **Status colors are fixed.** Success, warning, danger and info never take the brand color.
9. **Accessibility is a gate.** WCAG AA contrast (4.5:1 for text), keyboard access, visible focus, `prefers-reduced-motion` respected.
10. **Fonts are OFL only**, self-hosted through Fontsource packages.
11. **Do not copy third-party animation components into the product** (React Bits is MIT + Commons Clause; permission pending). Build our own effects in `packages/motion`.
12. **Plain language in the UI.** Users are not developers. Errors say what happened and what to do next.

## How to work in this repo

- Start each task by finding its milestone in [docs/12-roadmap.md](docs/12-roadmap.md) and meeting its acceptance criteria.
- Small, reviewable commits. One concern per pull request.
- Add or update tests with every behavior change. Run `pnpm typecheck && pnpm lint && pnpm test` before declaring work done.
- If a doc and the code disagree, stop and ask; don't silently pick one.
- If you make a decision the docs don't cover, add it to [docs/13-decisions-and-open-questions.md](docs/13-decisions-and-open-questions.md) in the same pull request.
- Free-tier limits, prices and third-party APIs change often. Verify against the provider's current docs before relying on a number in these docs.

## Glossary

| Term | Meaning |
| --- | --- |
| BYOK | Bring your own key: the user connects their own AI and service keys |
| Product spec | The structured JSON description of the app to build (`packages/spec`) |
| Style | One of 18 visual rule sets (layout, shape, type, component recipes) |
| Palette | A set of colors that fills a style's color slots |
| Brand kit | Palette, fonts, favicons, icons and images derived from the user's logo |
| Build | One run of the generation pipeline for one project |
| Checkpoint | Saved build state that lets a paused build resume |
| Readiness score | 0–100 score computed from automated checks, with plain-language findings |
| Motion level | Off, Subtle or Expressive animation setting for a generated app |
